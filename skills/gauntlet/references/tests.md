# Test Coverage & Quality Review

Answer three questions about the diff: **is the new functionality sufficiently tested**, **are those tests actually good**, and **which properties must always hold**? Start by naming the 2–3 riskiest behaviors in the diff — tricky logic, parsing, boundary math, auth, concurrency — and weight your findings there; a uniform sweep that spends equal effort on trivial and risky code misses where bugs actually live. Then locate the tests that correspond to the changed code (same-name test files, `test/`, `spec/`, `__tests__/`, co-located `.test.*`/`.spec.*` files) — read them, don't assume.

**Coverage — is anything untested?**
1. **New behavior with no test at all**: every new public function, endpoint, component behavior, or branch of business logic in the diff should have at least one test exercising it. Map each changed unit to its tests; report the ones with none.
2. **Changed behavior with unchanged tests**: if the diff alters logic but no test file changed, either the tests are too loose to notice (bad) or the behavior is untested (also bad) — flag it either way.
3. **Edge and failure paths**: error handling, empty/null inputs, boundary values, timeouts, and rejected promises introduced in the diff need tests too, not just the happy path. New guards/validation deserve a test proving they reject bad input. A fake for a boundary (network, third-party API, queue) that only ever succeeds counts here: new code that calls one needs at least one test where the fake times out, errors, or returns an empty or partial response, and for webhooks or message queues, delivers the same message twice.
4. **Regression anchors**: if the diff fixes a bug, there must be a test that fails on the old code and passes on the new — otherwise the bug can silently return.
5. Calibrate: don't demand tests for trivial passthroughs, generated code, pure config, or one-line delegation, or for inputs the types already rule out. When a bad input is reachable only because a signature is looser than the function's real domain, recommend narrowing the type (a discriminated union, a branded or enum type) rather than a test for the impossible case. Report *material* gaps, ranked by the risk of the untested code breaking silently.

**Quality — are the existing/new tests good?**
1. **Tautological tests**: tests that mock the unit under test, assert the mock was called with what it was stubbed to return, or restate the implementation — these pass no matter what and are worse than no test. A quieter form: the expected value is computed with the same helper, constant, or fixture builder the production code uses, so the test shares the code's mistakes. Expected values come from the spec, a hand calculation, or an independent restatement.
2. **Testing implementation, not behavior**: asserting on private state, internal call order, or exact markup/snapshots when the contract is the observable output. These break on refactors and pass on real bugs.
3. **Over-mocking**: so many collaborators stubbed that no real code path runs. Prefer real objects for cheap in-process collaborators; mock only true boundaries (network, clock, filesystem, third-party APIs). (A boundary fake that never fails is a coverage gap; report it under Coverage item 3, not here.)
4. **Weak assertions**: `assert result` / `toBeTruthy()` / "doesn't throw" where a specific expected value exists; asserting only part of the result when the rest matters.
5. **Nondeterminism**: reliance on wall-clock time, real network, sleep-based waits, iteration order, or shared mutable state between tests — flaky tests train people to ignore failures. For time-dependent logic (crons, expiry, windows like "last 24h"), the fix is to pass the clock or `now` in so the test sets time directly, not to add sleeps or a wider tolerance. The same fix applies to any hidden state the code reads (a blob or cache, env, a module-level variable): pass it in so the test is `(state, input) → result` with no setup choreography.
6. **Missing negative space**: tests that only confirm the feature works, never that it correctly refuses/fails (authz denied, validation rejects, error surfaces to the caller).
7. **Test hygiene**: misleading test names, dead/skipped tests touching the changed code (`xit`, `skip`, commented-out), copy-pasted tests that don't vary the thing their name claims to test.
8. **Degenerate inputs**: test inputs too symmetric or uniform to tell a correct implementation from a plausibly-wrong one — palindromes in roundtrip/reversal tests, all-same-value buffers, identical values on both sides of a swap, zero where sign matters. Ask: would this input still pass if the implementation reversed the order, swapped the arguments, or was off by one? If yes, flag it.

**Properties — what must always hold?**
Example-based tests are written by the same agent that wrote the code and share its blind spots. For each of the riskiest behaviors you named, ask whether it has a property: a statement that should hold for every input, checked against many generated inputs. If it does and no test checks it, that's a finding. Properties worth looking for:
- **Invariant**: parts sum to the whole (a rollup equals the sum of its rows, before and after any limit or grouping), a count never goes negative, output stays sorted or unique. Sum and associativity invariants don't hold exactly for floats: use integers (cents, counts) or assert within a stated tolerance.
- **Metamorphic**: when the exact expected output is hard to compute, state how the output must change when the input changes. Adding a row never lowers a total; filtering a superset returns a superset of the results; widening a date window never drops an item; reordering the input doesn't change an aggregate.
- **Round-trip**: decode(encode(x)) == x for parsers, serializers, normalizers and escaping.
- **Idempotency**: running a normalization, migration, retry or upsert twice equals running it once.
- **Guard boundary**: a predicate that classifies inputs (root path, allowed host, valid code) agrees with a plain restatement of its rule, written from the spec or contract rather than from the code, on generated near-miss inputs (`""`, `"."`, `"/."`, `"//"`, trailing or doubled separators, case variants, unicode lookalikes).
- **Stateful sequence**: only when the diff carries state between calls (snapshots, caches, queues, retries, counters). Generate a random sequence of operations, including skipped, repeated, out-of-order and interrupted ones (a crash between read and write, two overlapping runs of the same cron), and check the invariant after every step, not just at the end.
- **Equivalence (differential)**: for a refactor, rewrite or migration of existing behavior, the new code returns the same result as the old code on the same inputs, with any intended differences listed explicitly. If the old code won't survive the diff, record its outputs on a spread of inputs as a golden file before the change and compare the new code against that.

For each one, write down the property in one sentence, the input domain and how to generate it, and the test file to put it in. When the domain is small and finite (an enum, a status set, a few booleans, every entry in a config list), loop over all of it instead of sampling. If the repo already uses a property-testing library (fast-check, Hypothesis, proptest, Rantly, PropCheck, ...), use it. If not, specify a plain loop over a seeded random generator (a small seedable PRNG where the language's built-in one can't be seeded) plus the hand-picked near-misses in the existing test framework, with the seed and the failing input in the assertion message: adding a library is a new dependency, so mention it as optional and don't require it. A property gap over code you believe is correct is a `Nit` under the grading rule; the fix phase still writes it, and if it fails, the fix phase checks the counterexample against the intended contract to decide whether the code or the property is wrong.

For each finding, state what's untested or wrong, why it matters (what real bug would slip through), and the specific test to add or fix — concrete enough that the fix phase can write it. Don't pad the report with praise for covered areas; a short "covered adequately: X, Y" line is enough.
