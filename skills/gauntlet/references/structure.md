# Reuse & Structure Review

**Part A — the ladder.** Walk the change down this ladder and flag whatever skips a rung — the best code is the code that was never written.

1. **Does this need to exist at all?** YAGNI. If removing the code changes nothing observable, delete it. Watch for speculative abstractions, dead branches, scaffolding for hypothetical futures, single-consumer indirection.
2. **Stdlib?** Flag hand-rolled code for things the standard library already provides (date parsing, URL parsing, hashing, collection ops, etc.).
3. **Native platform / framework?** Flag custom wrappers when a native element, browser API, or framework primitive already does it (`<input type="date">`, `URL`, `Intl`, Rails helpers, ActiveSupport methods, framework form/validation primitives).
4. **Installed dependency?** Check `Gemfile.lock`, `package.json`, etc. — don't add new code or new deps when something already pulled in covers it.
5. **Existing utility or helper in this codebase?** Look in utility directories, shared modules, and files adjacent to the changed ones. Flag new functions that duplicate existing functionality and inline logic that could call an existing utility (hand-rolled string manipulation, manual path handling, custom environment checks, ad-hoc type guards).
6. **One line?** Flag multi-line implementations where a one-liner would do.

**Part B — structure (folded in from `pstack:thermo-nuclear-code-quality-review`).** Be ambitious: look for the reframing that makes whole branches, modes, helpers or layers disappear, not a tidier arrangement of the same complexity. A refactor that moves code around without reducing the number of concepts a reader has to hold isn't a fix.

**Fix or drop.** There is no report-only bucket: nothing acts on a finding parked in a PR body, so a structural finding is either fixed in this change or not raised. Report one only if the fix is **contained**: it stays within files the diff touches (or a new helper/module they extract into), needs no migration or backfill, and doesn't change the behavior of callers outside the diff. Otherwise drop it — don't mention it. Prefer a few high-conviction findings over a list of nits.

7. **Code-judo reframing**: a restructuring that keeps behavior but deletes complexity — change the state model so conditionals vanish, turn special cases into one default flow, make the feature a natural extension of an existing abstraction. Describe the reframed shape concretely enough to implement.
8. **File crossing 1,000 lines**: the diff takes a file from under 1k lines to over. Say which file, its before/after line count, and the extraction to make (helper, module, subcomponent). Skip if the file is still clearly organized.
9. **Ad-hoc conditionals and mode flags in unrelated flows**: a new one-off `if`, special case, boolean/nullable mode, or flag threaded through a path that otherwise has nothing to do with the change, or narrow edge-case handling dropped into an already busy function. Name the path it tangles and where the logic should move (policy object, dedicated helper, the canonical layer that already owns this decision).
10. **Duplication this diff adds to**: the diff adds another copy of something already repeated (a helper, a constant list, a test login flow), or repeated conditionals that signal a missing model. Fold the copies the diff touches into one shared helper or type; leave untouched copies elsewhere alone.
11. **Wrong layer**: feature-specific logic leaking into a shared/general-purpose module, or logic added somewhere other than the module that already owns the concept. Move it to its canonical home.
12. **Thin wrappers and magic**: identity wrappers, pass-through helpers, or generic mechanisms that hide a simple data shape. Delete the layer or replace it with the direct flow.
13. **Muddy type boundaries**: new casts, `any`/`unknown`, unnecessary optionality, ad-hoc object shapes, or silent fallbacks papering over an unclear invariant. Make the contract explicit (typed model, discriminated union, required field) so the control flow simplifies.
14. **Non-atomic updates**: related writes that can leave state half-applied when an atomic structure (single update, transaction, returning the value instead of mutating then restoring) is obvious.
15. **Definitions the diff orphans**: for each call, import or dependency the diff removes, grep the whole repo (including tests, scripts, configs, routes, and string or dynamic references like `send(:name)` or `import()`) for the definition's remaining references. If none are left, delete the definition, and also the package or gem when the dependency is no longer used. This is a contained fix even outside the diff's files, because removing unreferenced code changes nothing observable. Skip public API other repos consume, such as a published package's exports or a route an external client calls. When the repo has a `package.json` or `Gemfile.lock`, run `<skill dir>/scripts/dead-code.sh` first (`<skill dir>/references/dead-code.md` covers its exit codes and the runtime references it misses): it lists exactly what the branch newly orphans, and the grep confirms each one.

Lazy, not negligent: trust-boundary validation, data-loss handling, security, and accessibility are never on the chopping block. Don't recommend deleting those even when they look like ceremony.
